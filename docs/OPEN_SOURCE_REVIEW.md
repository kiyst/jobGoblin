## 1. kalil0321/ats-scrapers

**Reproducibility.** Repository: <https://github.com/kalil0321/ats-scrapers> (URL unchanged, no redirect). Reviewed commit: [`f654221f5236f24360719008764b23c5939fbce8`](https://github.com/kalil0321/ats-scrapers/commit/f654221f5236f24360719008764b23c5939fbce8) (tip of `main`, authored 2026-08-23T17:19:26Z). Reviewed at: **2026-08-23**. License: MIT, raw file at the reviewed commit: <https://github.com/kalil0321/ats-scrapers/blob/f654221f5236f24360719008764b23c5939fbce8/LICENSE>.

**1. Problem solved.** Ingestion of job postings directly from ATS platforms rather than aggregator sites. Confirmed (by file tree + passing per-platform test files, not just README claims) implementations for all of Greenhouse, Lever, Workday, Ashby, SmartRecruiters, iCIMS, Workable, SuccessFactors, Oracle, Personio, BambooHR, Dayforce, Jobvite, and UKG, plus ~40 more (ADP, Avature, Taleo, Recruitee, Rippling, Teamtailor, etc.) and first-party company APIs (Amazon, Apple, Google, Meta, Tesla, Uber, ByteDance, USAJobs). 122 scraper files, 135 test files (counts as of the original pass; not recounted file-by-file in this revision, since the reviewed commit's HEAD-of-main status was the target of this pass, not a full re-audit of file counts).

**2. Architecture.** `src/ats_scrapers/{__init__.py, client.py, exceptions.py, fetch.py, manifest.py, models.py, resolve.py, scrapers/, enrichment/}`; repo-only extras `pipeline/`, `ats-companies/`, `docs/`, `examples/`, `scripts/`, `tests/`. `scrapers/base.py` holds the abstraction; one module per ATS.

**3. Job acquisition.** Two paths: (a) live scraping via `BaseScraper.fetch()`/`afetch()` against each ATS's own (mostly public) JSON endpoints; (b) a pre-built hosted dataset (Parquet/CSV snapshots behind a manifest URL, default `https://storage.stapply.ai/jobhive/v1/manifest.json`) consumed through `Client.search()/load()/companies()/find_company()`, returning pandas DataFrames with no scraping or API key required. The dataset path is the documented default; live scraping is an opt-in extra (`pip install "ats-scrapers[scrapers]"`).

**4. Normalization.** Pydantic v2 `Job` model: identity (`global_id`, `url`, `title`, `company`, `ats_type`, `ats_id`), location (`location`, `country_iso`, `region`, `lat`, `lon`, `is_remote`), `Salary` (currency/period/min/max/summary), classification (`experience`, `employment_type`, `department`, `team`, `requisition_id`, `apply_url`, `commitment`), timing (`posted_at`, `fetched_at`, `application_deadline`), plus a `raw` overflow dict. `global_id` auto-derives as `{ats_type}:{ats_id}` with a UUID4 fallback. `ATSType` is a `StrEnum` with 60+ values.

**5. Source-specific/raw data.** Preserved via `Job.raw: dict`. Confirmed as an active pattern in commit history (e.g. a commit specifically adds Workday `startDate`/`endDate` into `Job.raw`), not just a schema placeholder.

**6. Failure handling.** Custom exception hierarchy: `CompanyNotFoundError` (404), `MalformedJSONError`, `RetryExhaustedError`, `ScraperError`. `fetch.py` implements exponential backoff (`DEFAULT_RETRIES=3`, base delay 1.5s, max 30s, honors numeric `Retry-After`) on 408/429/5xx and network errors. **Evidence, re-confirmed at the reviewed commit:** `src/ats_scrapers/fetch.py` lines 78–81 define exactly `DEFAULT_RETRIES = 3`, `DEFAULT_RETRY_BASE_DELAY = 1.5`, `DEFAULT_MAX_RETRY_DELAY = 30.0`, `DEFAULT_TIMEOUT = 30.0` — permalink: <https://github.com/kalil0321/ats-scrapers/blob/f654221f5236f24360719008764b23c5939fbce8/src/ats_scrapers/fetch.py#L78-L81>. When blocked (403/406), an optional escalation path (`fetch_escalate=True`) reruns the request through a TLS/h2-impersonation client (`httpcloak`/`cloakbrowser`) via `asyncio.to_thread()`.

**7. Concurrency.** Async-first via `httpx`; `BaseScraper.afetch()` is the primary interface with a sync `fetch()` wrapper. `aiohttp` and the cloak-browser escalation path are optional extras, not core dependencies.

**8. Duplicate handling.** No cross-source dedup logic observed within the library itself (it's a per-ATS ingestion layer, not a cross-source aggregator) — dedup is left to the consumer. `global_id` gives a stable per-(ats_type, ats_id) key useful as a building block.

**9. Persistence.** None built in beyond the hosted dataset's own storage (Cloudflare-fronted bucket) — the library returns in-memory `Job`/DataFrame objects; persistence is the caller's responsibility.

**10. What to reuse.** The Pydantic `Job` schema as a strong starting point for our own normalized job model; `resolve.py`'s deterministic URL-to-ATS matching (path-host table, subdomain-suffix table, regex full-URL matching for tenant hosts like Workday/Taleo/iCIMS, plus SSRF guards rejecting localhost/private IPs and spoofed hosts) — genuinely production-grade and worth using directly rather than reimplementing; the `ScraperRegistry` + `@register(ats)` decorator pattern; the retry/backoff constants and escalation-on-block strategy (see permalink above).

**11. What to reimplement ourselves.** Cross-source/cross-listing deduplication (not attempted by the library); a `health()`-style readiness check (none exists — no `/health` or self-test method was found); persistence and our own retry-ownership decision (avoid double-retrying if we also wrap calls with platform-level retry logic).

**12. What to avoid copying.** Nothing objectionable found — no auto-apply or unsafe collection behavior observed. The one caution: using the opt-in browser-impersonation escalation feature against a given ATS's wishes is an engineering/compliance risk consideration (not a legal opinion) that should be evaluated per-target before enabling it.

**13. License obligations.** MIT (verbatim re-confirmed at the reviewed commit via the raw LICENSE file above and the GitHub API `license` field), copyright "Kalil Bouzigues," 2026. Standard permissive terms — attribution/copyright notice must be preserved in redistributions; no copyleft obligations.

**14. Current activity.** Very active: at the time of this revision the tip of `main` was pushed 2026-08-23T17:19:26Z (same day as this research), from a distinct contributor (not the sole maintainer) merging PR #258 — consistent with the "multiple contributors, high velocity" read from the original pass. Repo created 2025-10-28 (under a year old). 135 stars / 30 forks per the original pass (star/fork counts are not re-verified in this revision and are not being used to justify any classification decision, per the reviewer's guidance). Open issues/PRs: 1 open issue, 38–39 open PRs — still a sizeable backlog whose review/merge cadence remains unverified.

**15. Fit behind `DiscoveryProvider`.** As `AtsScrapersProvider`: `discover()` maps to `resolve_careers_url(url)` + `get_scraper_for_url(url).afetch()` for live discovery, or `Client.search()/find_company()` for dataset-backed discovery — the adapter must choose (or expose both) since the library doesn't unify the two modes; `capabilities()` derives from `ScraperRegistry.all()` keys; `health()` has no library equivalent and must be synthesized (e.g. ping the manifest URL or run a known-good scrape). Bridging work: translate `Job` (Pydantic) into our own model, prefer the async `afetch()` path, translate the library's exceptions into our discovery-error types, and decide which layer (library or platform) owns retry/backoff to avoid duplication.

## 2. python-jobspy (canonical repo: speedyapply/JobSpy)

**Reproducibility.** Repository: <https://github.com/speedyapply/JobSpy>. `cullenwatson/JobSpy` (the original location) was re-checked this pass and still returns an HTTP redirect ("Moved Permanently") to the `speedyapply` org repo — confirming the rename is still in effect, not reverted. Reviewed commit: [`fda080a373e8226f3fd60635323f5da9af9892b1`](https://github.com/speedyapply/JobSpy/commit/fda080a373e8226f3fd60635323f5da9af9892b1) (tip of `main`, authored 2026-02-18T19:39:52Z — this is the same HEAD as the prior pass; the repo has had no new commits since). Reviewed at: **2026-08-23**. License: MIT, raw file at the reviewed commit: <https://github.com/speedyapply/JobSpy/blob/fda080a373e8226f3fd60635323f5da9af9892b1/LICENSE>.

**Canonical-repo note.** PyPI's `python-jobspy` project page links to `github.com/cullenwatson/JobSpy`, which now redirects to **`github.com/speedyapply/JobSpy`** — the original author moved the project into an org. Separately, the plain PyPI package name `jobspy` is an **unrelated** LGPL-2.1 Redis job-coordination library (`josiahcarlson/jobs`) — do not confuse the two when pinning dependencies.

**1. Problem solved.** Concurrent scraping across general job boards. `jobspy/__init__.py`'s `SCRAPER_MAPPING` registers exactly 8 sites: LinkedIn, Indeed, ZipRecruiter, Glassdoor, Google, Bayt, Naukri, BDJobs.

**2. Architecture.** One subpackage per site (`jobspy/linkedin/`, `jobspy/indeed/`, etc.), each with its own `__init__.py`/exceptions/constants; shared `jobspy/model.py` (Pydantic `JobPost`, `JobResponse`, `Compensation`, `Location`, `Country`, `Site`, `ScraperInput`, abstract `Scraper` base) and `jobspy/util.py` (session/proxy/retry helpers, salary regex extraction).

**3. Acquisition / search parameters.** `scrape_jobs(site_name, search_term, google_search_term, location, distance=50, is_remote, job_type, easy_apply, results_wanted=15, country_indeed="usa", proxies, ca_cert, description_format="markdown", linkedin_fetch_description=False, linkedin_company_ids, offset=0, hours_old, enforce_annual_salary=False, verbose=0, user_agent, **kwargs)` — returns a `pandas.DataFrame`.

**4. Normalization.** Each site scraper returns a `JobPost` Pydantic model (id, title, company_name, job_url, job_url_direct, location, description, compensation, date_posted, job_type, emails, is_remote, plus site-specific extras like Naukri's `skills`/`company_rating`). `scrape_jobs()` flattens these into rows, adds a `site` column, and concatenates into one ordered/sorted DataFrame.

**5. Source-specific/raw data.** Site-specific extra fields are kept on the per-site `JobPost` subclasses/extras (e.g. Naukri's `experience_range`), but there is no generic "raw payload" overflow field comparable to `ats-scrapers`' `raw` dict — once flattened into the DataFrame, provider-specific nuance not modeled explicitly is lost.

**6. Failure handling — critical finding, re-confirmed at the reviewed commit.** Behavior is **inconsistent per site and unsafe at the top level**. The orchestration loop in `jobspy/__init__.py` at lines 125–126 (`for future in as_completed(future_to_site): site_value, scraped_data = future.result()`) has **no try/except around it** — permalink: <https://github.com/speedyapply/JobSpy/blob/fda080a373e8226f3fd60635323f5da9af9892b1/jobspy/__init__.py#L125-L126> — so any uncaught exception from one site's thread propagates and kills the entire `scrape_jobs()` call, discarding already-completed results from other sites. Glassdoor's own `scrape()` catches broadly and returns a graceful partial `JobResponse`; **LinkedIn does not** — in `jobspy/linkedin/__init__.py`, the job-card loop wraps `_process_job()` in a try/except that only re-raises (lines 156–164: `try: ... except Exception as e: raise LinkedInException(str(e))`), with nothing in an enclosing scope catching it — permalink: <https://github.com/speedyapply/JobSpy/blob/fda080a373e8226f3fd60635323f5da9af9892b1/jobspy/linkedin/__init__.py#L156-L164>. (There is a separate try/except around the HTTP request itself at lines 117–134 that returns a partial `JobResponse` on request failure, but it does not cover the job-card processing loop where the re-raise happens.) Any wrapper **must** call sites independently (or wrap each per-site call with its own try/except) rather than trust the library's multi-site aggregation.

**7. Concurrency.** `ThreadPoolExecutor` with one thread per requested site, collected via `as_completed()` — thread-based, not async, and not configurable for max workers beyond the site count.

**8. Duplicate handling.** None — no cross-site or cross-run dedup logic; every call returns raw scraped rows.

**9. Persistence.** None — pure in-process scrape returning a DataFrame; persistence is the caller's job.

**10. What to reuse.** The salary-normalization concept (`Compensation`/`SalarySource` distinguishing `DIRECT_DATA` vs. regex-mined `DESCRIPTION`, `enforce_annual_salary` to normalize to yearly) as a pattern, even if we reimplement the regex ourselves — the library's own docstring admits the salary regex is a `"TODO: Needs test cases... may not cover all edge cases"`, so treat it as a starting point, not gospel.

**11. What to reimplement ourselves.** Per-site failure isolation (call `scrape_jobs()` once per site inside our own try/except, not as a multi-site list); a `raw` passthrough field for provider nuance; a `health()` mechanism tracking per-site success rates, since Google and ZipRecruiter were reported broken (HTTP 403) in an open issue (#302) with reports spanning 2025-09 through at least 2025-07; any circuit-breaker/timeout beyond LinkedIn's hardcoded 10s (confirmed again at the reviewed commit: the LinkedIn HTTP request at line ~120 passes `timeout=10`).

**12. What to avoid copying.** The library's own optimistic assumption that a multi-site call degrades gracefully — it does not, uniformly. Also avoid relying on the PyPI-published version for recent fixes; it is roughly 13 months behind GitHub `main` as of this research.

**13. License obligations.** MIT (verbatim re-confirmed at the reviewed commit), "Copyright (c) 2023 Cullen Watson." Standard permissive terms, no copyleft. No ToS/legal disclaimer of any kind appears in the README regarding scraping LinkedIn/Indeed/Glassdoor. As with all ToS-adjacent statements in this document, this is a factual observation about the README's contents, not a legal assessment of scraping legality — **that risk is entirely on us to evaluate and disclose**, not something the upstream project addresses.

**14. Current activity.** GitHub: last push 2026-02-18 (unchanged HEAD, confirmed this pass — no new commits in the intervening months), 61 open issues with visible community engagement (an informal maintainer responds), but slow resolution — issue #302 (Google/ZipRecruiter 403s, opened 2025-09) had 13 comments and was still unresolved as of reports into 2026-07 (not independently re-checked in this pass). PyPI: last published release 1.1.82 on 2025-07-28 — over a year stale relative to GitHub `main`, meaning `pip install python-jobspy` today gets known-broken behavior for at least two of the eight sites until/unless a new release is cut.

**15. Fit behind `DiscoveryProvider`.** As `JobSpyProvider`: `discover()` should call `scrape_jobs(site_name=[single_site], ...)` once per site inside its own try/except loop (never pass a multi-site list, to avoid the all-or-nothing failure mode); convert DataFrame rows to our domain model immediately rather than leaking pandas past the adapter; `health()` should track recent per-site success/failure given known-brittle sites; `capabilities()` reports the literal 8-site list with an explicit caveat that not all are reliably functional at any given time; wrap each per-site call with our own outer timeout since the library provides none beyond LinkedIn's hardcoded 10s.

- **peviitor-ro** — a genuinely relevant multi-repo reference for "many heterogeneous per-company scrapers feeding one normalized index," worth a closer look if we want more real-world dedup/index-merge examples, but PHP/Solr-based. **License correction from this pass:** the core `api` repo, `Scrapy_peviitor_jobs`, and `Scrapers_Cristi_Olteanu` all report `license: null` (confirmed via the GitHub API at the commits recorded above) — only `JobsScrapers` is actually MIT. Do not treat any of the four as a dependency; unlicensed ones in particular should not be code-reused even for reference snippets beyond reading them.
- **dedupeio/dedupe** and **worldbank/FuzzyAI** — both flagged as candidate *dependencies* for job dedup rather than mere references, but neither has been evaluated deeply enough here to assign Reuse Type A/B; `dedupe`'s last push (2025-07-29, re-confirmed unchanged this pass) is borderline against our 12–18 month activity bar and should be rechecked before adoption. `FuzzyAI`'s MIT license carries an additional `WB-IGO-RIDER.md` at the repo root (confirmed present, linked above) — read it before adopting, since World Bank/IGO riders sometimes add terms beyond plain MIT.
- **scrapinghub/extruct** — likely useful as a lightweight building block for generic JSON-LD `JobPosting` parsing (see Source Connectors doc); its license is now **confirmed BSD-3-Clause** via the GitHub API (previously flagged unverified in this doc).
- **spatie/schema-org / crwlrsoft/schema-org** — PHP, not directly usable, but a good field-modeling reference for our own `JobPosting` schema. `crwlrsoft/schema-org`'s reviewed commit is also its `v0.4` tag point, which is a more meaningful anchor than an arbitrary HEAD for a small, infrequently-tagged library.

## Honesty on uncertainty

Explicitly unverified in this research pass: `ats-scrapers`' PR review/merge cadence beyond raw counts; whether its hosted-dataset endpoint has any uptime guarantee; exception-handling behavior for JobSpy's Google/Bayt/Naukri/BDJobs/ZipRecruiter scrapers (only LinkedIn and Glassdoor were inspected at the code level); `job-board-aggregator`'s Common-Crawl harvesting pipeline (described in its README but not present in its source tree at the reviewed commit); full contents of OpenPostings' `chrome-extension/` directory and all ~85 of its ATS service modules (only Greenhouse was inspected directly); star/fork counts across all repos (recorded once at the original pass, not re-polled in this reproducibility revision, and explicitly not used to drive any reuse-type decision); and the current, full text of any platform's Terms of Service beyond what's linked in [`SOURCE_CONNECTORS.md`](./SOURCE_CONNECTORS.md) — see the legal-language disclaimer near the top of this document.

Also newly noted in this pass: for `worldbank/FuzzyAI` and `scrapinghub/extruct`, the GitHub API's `pushed_at` timestamp is later than the tip commit found on each repo's default branch via its commits feed — most likely a push to a tag or non-default ref rather than new default-branch development. This is flagged as a reproducibility quirk worth knowing about (it means "last push" and "last commit on the branch you'd actually pull" can diverge), not as evidence of undisclosed activity.
